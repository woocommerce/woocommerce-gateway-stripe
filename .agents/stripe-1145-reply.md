**Root cause confirmed and fixed.** The charge ID isn't being written to `_transaction_id` for express checkout (Apple Pay / Google Pay) orders because they go through the confirmation-token flow, where the ID is stored only via `process_response()` → WooCommerce core's `payment_complete( $charge_id )`. Core only calls `set_transaction_id()` when the order is in a `PAYMENT_COMPLETE_STATUSES` status (pending/on-hold/failed/etc.) — and these orders are typically already `processing`/`completed` by then, so it's skipped. `process_response()` still adds the "Stripe charge complete (Charge ID: …)" note, which is exactly why the charge ID appears in the notes but `_transaction_id` stays empty and `process_refund()` bails. Same class of bug as the legacy-flow fix in #269/#270, now addressed for the confirmation-token flow.

**Fix:** woocommerce/woocommerce-gateway-stripe#5481 (issue #5480) persists the charge ID as `_transaction_id` after `process_response()` in the confirmation-token flow, so these orders are refundable going forward.

**Already-affected orders:** the related #5479 (issue #5478) adds a refund-time fallback that recovers the charge ID from the stored payment intent, so existing orders that are already missing `_transaction_id` become refundable too (and self-heal). Between the two PRs, both new and historical orders are covered.
